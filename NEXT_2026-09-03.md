### The seed sweep holds — and the single-seed report was misleading

| seed | clean dB | clean JOD | hard dB | hard JOD | clean CVVDP |
|---|---:|---:|---:|---:|---:|
| 20260901 | +0.07 | +0.113 | +1.24 | +0.389 | 9.561 |
| 2 | +0.71 | +0.068 | +0.96 | +0.308 | 9.516 |
| 3 | +0.45 | +0.089 | +1.18 | +0.358 | 9.537 |
| **mean ± sd** | **+0.41 ± 0.33** | **+0.090 ± 0.023** | **+1.12 ± 0.15** | **+0.352 ± 0.041** | |

All three positive on all four measures; all three clean CVVDP above every
fixed alternative (best of those 9.452). Seed 20260901 turned out to be the
**worst** of the three on clean dB and the **best** on clean JOD, so the old
headline understated dB sixfold and overstated JOD by a quarter. The paper now
reports mean ± sd everywhere.

### §8's selection claim is half right

Step 72,000 scored: composite **−1.36 dB vs the shipped checkpoint's −1.57**, so
median-smoothed selection *would* have picked better on the criterion it
optimises (clean PU21 +0.55 dB). But CVVDP is **worse on both conditions**
(−0.052 clean, −0.071 hard). Smoothing the selector removed the noise; it did
not fix selecting on the wrong quantity. §8 now says both halves.

## Tested and dropped: the chromaticity shift (3 Sep)

Two photographs suggested RUDRA desaturates highlights toward green (red share
−0.07, green +0.05 in the brightest 1%). Measured on all 429 held-out frames
with `training/analyze_chroma_shift.py`, it does not survive:

| band | share of pixels | green shift | vs the reference | frames agreeing on sign |
|---|---:|---:|---|---:|
| < 20 nits | 41.2% | +0.005 | towards | 33% |
| 20–203 | 46.1% | +0.000 | — | 32% |
| 203–1000 | 11.4% | −0.001 | towards | 64% |
| > 1000 | 1.3% | +0.005 | **away** (0.0057 → 0.0110) | 50% |

Only the top band moves away from the truth, it is **ten times smaller** than
on the photographs, it covers 1.3% of pixels, and 50% sign agreement is a coin
flip. Both test photographs were saturated sunsets whose bright regions are
nearly one hue; the split's bright band averages near-neutral, so per-frame
shifts cancel. Real on single-hue highlights, not a property of the model.
**Not going in the paper.**

The first run of that script reported a 0.096 green error in deep shadow that
was entirely an artifact: chromaticity is undefined at black, and averaging
near-zero triples divided by a floor produces numbers that do not sum to 1. The
script now requires 0.1 nits of energy in all three trees before a pixel counts.

## Remaining, in order

### 1. Comparison against a published method — the largest gap

Every number in the paper is against our own analytic baseline. The harness for
this is now built and tested; what remains is running someone else's code.

**Step 1 — export the inputs.** DONE: 429 PNGs are in
`E:\RUDRA_v3_20260822\bench\clean\sdr\<scene>\<asset>.png`.

**Step 2 — run their code.** ExpandNet has a runner now, verified end to end
(clone, weights, their preprocessing, their `predict`, EXR out):

```powershell
git clone https://github.com/dmarnerides/hdr-expandnet.git
python training\run_expandnet.py --sdr E:\RUDRA_v3_20260822\bench\clean\sdr ^
    --repo hdr-expandnet --out E:\RUDRA_v3_20260822\bench\clean\expandnet_raw
```

~9 s/frame on CPU, so expect a couple of minutes on the 4080. Then import both
sides and score:

```powershell
python training\import_method_output.py --out E:\RUDRA_v3_20260822\bench\clean --from E:\RUDRA_v3_20260822\bench\clean\expandnet_raw --name expandnet
python training\import_method_output.py --out E:\RUDRA_v3_20260822\bench\clean --from E:\RUDRA_v3_20260822\bench\clean\shadow_v1 --name rudra_aligned
rudra bench E:\RUDRA_v3_20260822\bench\clean --nits-scale 203 --test-dir expandnet
rudra bench E:\RUDRA_v3_20260822\bench\clean --nits-scale 203 --test-dir rudra_aligned
```

The `rudra_aligned` row is not optional. It is RUDRA through the same per-frame
exposure fit ExpandNet gets, and without it the table hands the competitor a
free parameter and calls the result ours.

The other three methods (Santos 2020, HDRCNN, SingleHDR) have no runner yet.

§2 names four with public repos:

| method | repo | note |
|---|---|---|
| ExpandNet | `dmarnerides/hdr-expandnet` | lightest to run — start here |
| Santos 2020 | `marcelsan/Deep-HdrReconstruction` | PyTorch |
| HDRCNN | `gabrieleilertsen/hdrcnn` | TensorFlow 1.x, may need a container |
| SingleHDR | `alex04072000/SingleHDR` | multi-stage, heaviest |

**Step 3 — import and score** (CPU, ~1 min):

```powershell
python training\import_method_output.py --out E:\RUDRA_v3_20260822\bench\clean --from <their_output> --name expandnet
rudra bench E:\RUDRA_v3_20260822\bench\clean --nits-scale 203 --test-dir expandnet
```

**The alignment caveat, which the paper must state.** These methods predict
*relative* radiance — no absolute nit anchor — so the importer fits one global
scalar per frame before scoring, on the pixels the SDR input did not clip.
That is a free parameter RUDRA does not get: it predicts absolute nits and is
scored as it stands. Report the symmetric row too:

```powershell
python training\import_method_output.py --out E:\RUDRA_v3_20260822\bench\clean --from E:\RUDRA_v3_20260822\bench\clean\test --name test_aligned
rudra bench E:\RUDRA_v3_20260822\bench\clean --nits-scale 203 --test-dir test_aligned
```

If `test_aligned` is much better than `test`, the gap is exposure and the paper
should say so rather than bury it. `import_<name>.json` records the fitted
scales, any frames resized, and any the method dropped — all of which are
caveats on that table row, not details.

### 2. arXiv submission

```bash
bash paper/mkarxiv.sh     # -> paper/rudra-arxiv.tar.gz, verified to build flat
```

- **Source of truth is the markdown.** Never edit `paper/_body.tex` or
  `paper/_abstract.tex` — every build regenerates them from

  the tarball. No bibtex run needed (inline `thebibliography`).
- Categories: `eess.IV` primary, `cs.CV` cross-list.

  1,920.** Paste `paper/ABSTRACT_ARXIV.txt` (1,803) into the web form; the PDF
  keeps the full one. `build.sh` warns if the markdown abstract grows.
